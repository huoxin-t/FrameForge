# FrameForge｜视频格式转换桌面客户端

> 线上笔试项目规格、架构决策、三日开发计划与 AI 编码执行手册  
> 版本：1.0  
> 规划日期：2026-10-21  
> 目标平台：Windows 10/11 优先；架构尽量保留跨平台空间

---

## 0. 项目目标与验收原则

### 一句话介绍

FrameForge（帧铸）是一款本地运行的视频格式转换桌面客户端。用户可以导入多个视频，查看缩略图与媒体信息，选择输出容器和质量预设，批量转换，并查看进度、错误和输出文件。

### 本项目要证明什么

1. **客户端工程能力**：不是普通网页，而是 Electron 桌面应用，实际使用系统文件对话框、本地文件系统和 FFmpeg 子进程。
2. **AI 工程能力**：把需求拆成可验证的小阶段，限制模型改动范围，用测试结果而不是模型自述判断完成度，并记录决策、反馈、问题和修复过程。
3. **交付能力**：开发模式能运行、Windows 打包版本能启动、核心流程实测通过、README 清楚、GitHub 仓库整洁。
4. **产品意识**：用户能看懂每个按钮的作用，过程有反馈，失败可解释，重要文件不会被悄悄覆盖。

### 三天的范围取舍

**必须完成（P0）**

- Electron Windows 桌面窗口；不是仅部署到浏览器的 Web 页面。
- 通过系统文件选择框导入视频；最好支持拖拽导入。
- 通过 `ffprobe` 获取视频时长、分辨率、帧率、容器格式、视频/音频编码和文件大小。
- 通过 `ffmpeg` 生成并显示缩略图。
- 至少支持 MP4、MKV 两类输出容器，提供合理的默认编码参数。
- 转换真实可执行；展示队列、进度、成功、失败和取消状态。
- 支持选择输出目录；输出文件名冲突时不静默覆盖。
- 给出清楚的错误提示，例如源文件无效、FFmpeg 不可用、目标路径不可写。
- Windows 打包产物可启动；README 和会话记录完成。

**有时间再做（P1）**

- 视频拖放导入。
- 更多输出格式（例如 MOV、WebM），并根据实际可用编码器动态开放选项。
- H.265 高压缩预设（须先确认 FFmpeg 编译包包含对应编码器）。
- 任务历史、最近输出位置、键盘快捷键。
- 转换完成后显示“打开文件”和“打开输出目录”。

**明确不做（P2 / 排除）**

- 视频剪辑时间线、字幕编辑、滤镜、转场、AI 超分辨率。
- 用户系统、云端上传、服务端任务队列、数据库。
- 复杂的硬件加速选择；不同机器的显卡驱动与 FFmpeg 构建差异会扩大测试范围。
- 自定义 FFmpeg 命令输入框。任意命令执行风险高，且不是本题的考察重点。
- 为了显得丰富而创建没有实际功能的导航、按钮、统计卡片。

**完成定义：**不能以“页面渲染出来”作为完成。必须从真实视频文件开始，走完导入、信息读取、缩略图、参数选择、实际转码、输出文件验证和结果打开整个链路。

## 1. 技术选型

| 层 | 选择 | 原因 |
|---|---|---|
| 桌面运行时 | Electron | JavaScript/TypeScript 技术栈，适合本地文件和子进程工作流，三天内比引入 Rust/Tauri 学习成本更低 |
| UI | React + TypeScript | 组件边界清晰，类型可帮助 AI 编码模型减少接口拼错 |
| 构建 | Vite + electron-vite | 前端迭代快；主进程、预加载脚本和渲染进程可以分开构建 |
| 打包 | electron-builder | 生成 Windows 安装包或便携包；先保证 Windows 端可用 |
| 样式 | Tailwind CSS | 容易快速调整布局、密度、间距和视觉一致性 |
| 图标 | lucide-react | 统一线性图标，避免 emoji 作为主要界面图标 |
| 状态管理 | Zustand（可选） | 跨导入区、任务区共享状态；若实现规模很小，也可先使用 React 状态，避免为了架构而架构 |
| 媒体探测 | `ffprobe` CLI | 使用 JSON 输出读取元数据，不引入 FFmpeg API 绑定 |
| 媒体处理 | `ffmpeg` CLI | 子进程调用，读取进度并支持中止 |
| 配置持久化 | `electron-store` 或小型 JSON 配置 | 保存输出目录、窗口设置等非敏感偏好；不要为此引入数据库 |
| 测试 | Vitest + 少量手动端到端测试 | 纯函数和格式化逻辑自动测试；FFmpeg 与打包主流程必须实测 |

### 为什么不优先用 Tauri？

Tauri 是合理的桌面方案，但该任务三天限时，Electron 能直接复用 React/TypeScript 知识，FFmpeg 子进程管理和文件系统边界也更容易交给熟悉 Node.js 的 AI 编码模型实现。此处优化的是交付概率，而不是安装包体积。

### 关于 FFmpeg 依赖分发

推荐的开发策略：

1. 通过 npm 包（例如 `ffmpeg-static`、`ffprobe-static`）管理预编译二进制，或允许用户在设置页指定本机 FFmpeg 路径。
2. 启动时做一次环境检查，展示 `ffmpeg` / `ffprobe` 是否可用以及版本；检查失败要提供可执行的修复说明。
3. 不要把二进制直接提交进 Git 仓库；通过包管理器和打包配置处理。
4. **发布可下载安装包前，核对实际二进制发行包的构建选项与许可证义务。** FFmpeg 基础部分使用 LGPL，但某些可选组件可能使所用构建受 GPL 等条款影响；不能只因为 npm 包能安装就假设所有再分发义务都已解决。官方说明：https://ffmpeg.org/legal.html

为了按时交付，第一优先是让开发模式与 Windows 打包产物在同一台目标 Windows 机器上都能找到 FFmpeg。不要直到第三天才第一次打包。

## 2. 面向用户的产品设计

### 用户画像与主任务

典型用户是想把一批视频转成常用格式的人，不一定知道 codec、容器、CRF 或 bitrate 的含义。界面应让普通用户从预设开始，同时允许了解更多技术信息的人查看详细参数。

### 界面布局建议

默认窗口建议约 `1360 × 860`，支持缩放与窗口调整；低分辨率窗口下避免横向溢出。

```text
┌───────────────────────────────────────────────────────────────────────────────┐
│ FrameForge / 帧铸        本地处理 · 文件不会上传       FFmpeg ● 已就绪        │
├──────────────┬───────────────────────────────────────┬────────────────────────┤
│              │ 转换工作台                            │ 转换设置               │
│  转换        │                                       │                        │
│  任务队列    │ [添加视频] [添加文件夹(可选)]           │ 输出格式 [ MP4 ▼ ]      │
│  设置        │                                       │ 质量预设 [ 标准 ▼ ]     │
│              │ ┌───────────────────────────────────┐ │ 视频编码 H.264          │
│              │ │ 缩略图  文件名                     │ │ 质量     [CRF 23]       │
│              │ │         1920×1080 · 00:03:20        │ │ 音频     AAC 192 kbps   │
│              │ │         MP4 · H.264 · 145 MB       │ │                        │
│              │ └───────────────────────────────────┘ │ 输出到 [选择目录]       │
│              │ ┌───────────────────────────────────┐ │                        │
│              │ │ ... 其他文件 ...                  │ │ [开始转换]             │
│              │ └───────────────────────────────────┘ │                        │
├──────────────┴───────────────────────────────────────┴────────────────────────┤
│ 队列 2 个任务 · 正在转换 file.mp4                    42%    [取消当前任务]      │
└───────────────────────────────────────────────────────────────────────────────┘
```

布局不是必须逐像素照抄。重点是让导入文件、查看状态、选参数和启动转换处于同一工作空间，减少用户来回切页面。

### 信息层级

**顶栏**：产品名、简短的本地处理说明、FFmpeg 环境状态。  
**主区域**：视频文件列表 / 缩略图 / 元数据 / 每项状态。  
**右侧设置**：输出格式、质量预设、输出目录、开始转换按钮。  
**底部或独立任务视图**：整体进度、当前任务、取消操作、失败原因。  
**设置页**：FFmpeg 检测结果、版本、路径设置、应用信息与许可证说明。

### 产品细节

- 空状态要告诉用户“添加视频”以及支持什么格式，不要只放一个空白框。
- 导入后先展示文件行骨架 / “正在读取媒体信息”，避免长视频让用户误以为程序卡死。
- 缩略图生成失败时显示中性占位图，不能导致整个文件无法转换。
- 超长文件名显示省略号，但鼠标悬停可看完整路径。
- 文件大小统一展示 KB / MB / GB；时长统一显示 `hh:mm:ss`。
- 输出目录应清晰可见；开始前让用户知道文件将保存在哪里。
- 不要静默覆盖同名文件。默认生成 `_converted` 名称，若冲突则依次生成 `(1)`、`(2)`，也可向用户确认。
- 转换过程中应防止同一任务被重复点击启动。
- 100% 进度只有在 FFmpeg 以成功码退出并且输出文件存在、大小大于 0 时才能显示；不能根据进度字符串提前宣告成功。
- 失败信息要翻译成普通用户能读懂的说明，并提供“查看详细日志”。
- “取消”要实际终止子进程，并清理临时文件；不能只隐藏 UI 进度条。

## 3. 功能规格与验收条件

### F1. 导入视频

**用户操作**：点击“添加视频”打开系统多选文件对话框；拖拽支持可作为增强项。  
**行为**：验证文件存在、扩展名与媒体探测结果；为每个文件创建独立状态；重复导入同一路径时提示或忽略，不创建重复行。  
**验收**：至少可以一次导入多个文件；路径包含空格、中文时可正常处理。

### F2. 获取媒体信息

推荐命令形态：

```bash
ffprobe -v error -show_format -show_streams -of json "input-video.mp4"
```

实际实现必须用 `spawn(executablePath, args)` 传入参数数组，不要拼成一条 shell 字符串。解析 JSON 时定位第一个视频流和可选音频流。

建议字段：

```ts
interface VideoMetadata {
  durationSeconds: number | null;
  width: number | null;
  height: number | null;
  frameRate: number | null;
  containerFormat: string | null;
  videoCodec: string | null;
  audioCodec: string | null;
  hasAudio: boolean;
  fileSizeBytes: number;
}
```

帧率可能是 `30000/1001` 一类的分数，必须安全解析；遇到 `0/0`、缺失、N/A 时显示“未知”，不能显示 `NaN`。音频流缺失是合法情况，不应该让只含视频的文件失败。

**验收**：元数据与 FFprobe 输出基本一致；损坏文件要显示失败状态和可理解的原因；长时间任务不能阻塞 UI。

### F3. 生成缩略图

通过 FFmpeg 提取单帧，按固定宽度缩放，不应读取或解码整段视频到内存。

推荐处理逻辑：

1. 以视频大约第 1 秒处抽帧；
2. 很短的视频或首选时间失败时回退到第 0 秒；
3. 输出小尺寸 JPG/WEBP 临时图片；
4. 读取图片并通过受控 IPC 返回 `data:` URL，或用实现妥当的本地资源协议；
5. 失败时保留占位图和原视频信息。

**验收**：不同宽高比的视频不会把 UI 挤变形；中文路径可用；缩略图任务失败不会导致整个应用崩溃。

### F4. 转换参数

MVP 至少支持两种容器：MP4 与 MKV。可以把 MOV 作为加分项，但不要在没有验证的情况下承诺所有 codec/容器组合。

默认 MP4 建议参数：

```text
-c:v libx264 -preset medium -crf 23 -c:a aac -b:a 192k -movflags +faststart
```

对于 MKV，不传仅适用于 MP4/MOV 的 `-movflags +faststart`。应根据输出容器构建参数，而不是在所有格式上复用一条固定命令。

更友好的参数设计：

- **兼容优先**：MP4 + H.264 + AAC，CRF 23。
- **质量优先**：MP4/MKV + H.264 + AAC，CRF 20。
- **体积优先（可选）**：H.265/HEVC，前提是 FFmpeg 检测到 `libx265` 编码器；否则禁用选项并说明原因。

MVP 不必暴露所有 FFmpeg 参数。用“兼容优先 / 质量优先”两三个预设足以体现取舍。技术详情可以放进可展开的高级选项。

### F5. 任务队列和进度

状态枚举：

```ts
type JobStatus =
  | 'queued'
  | 'running'
  | 'completed'
  | 'failed'
  | 'canceled';
```

**队列策略**：三天版本只做单任务串行转换。多个视频按顺序执行，避免多个高负载进程争抢 CPU/磁盘，也更容易准确处理取消与错误。

进度建议优先使用 FFmpeg 的 `-progress pipe:1 -nostats` 输出，不要只用 stderr 文本正则猜进度。解析 `out_time=HH:MM:SS.microseconds` 与媒体时长计算进度；如需要使用 `out_time_us` / `out_time_ms`，应核实具体语义并写单元测试。进度上限在转换未成功退出前保持 99%。

必须处理：

- 成功退出且文件存在：`completed`。
- 非零退出：`failed`，保存可读错误和简短日志。
- 用户取消：`canceled`，终止子进程并清理临时输出。
- 应用关闭：提示有正在执行的任务；根据简化设计可先允许用户取消后退出。
- 某一任务失败：不能让后续任务队列整体停止，除非用户主动取消整个队列。

### F6. 输出文件安全

- 默认输出文件名使用原名称加 `_converted` 和目标扩展名。
- 转换先写同目录或同输出目录里的临时文件，成功后再改名为最终文件。
- 若任务失败或取消，清理临时文件；清理失败需记录日志。
- 不允许无意将输出路径设置为正在处理的输入路径。
- 对已存在目标文件使用唯一名称策略，不使用静默覆盖。

### F7. 日志与环境检查

设置页至少显示：

- FFmpeg 状态：已就绪 / 未找到 / 版本检查失败。
- FFmpeg 版本摘要。
- FFprobe 状态。
- 打开日志目录或复制错误详情的能力。

**不要在前端把任何内部异常直接用未经处理的堆栈弹窗给普通用户。** 详细日志供调试；主 UI 给出简洁、具体、可操作的失败说明。

### 为什么不能把所有东西都写在 React 页面里？

UI 进程应该负责界面状态和用户交互，主进程负责文件、子进程、路径与任务生命周期。这样可避免 React 组件卸载导致 FFmpeg 工作丢失、UI 卡顿、测试困难等问题。

### IPC API 建议

```ts
interface DesktopAPI {
  selectVideoFiles(): Promise<string[]>;
  selectOutputDirectory(): Promise<string | null>;
  inspectVideo(path: string): Promise<VideoInspectionResult>;
  getThumbnail(path: string): Promise<ThumbnailResult>;
  getFfmpegCapabilities(): Promise<FfmpegCapabilities>;
  startConversion(request: ConversionRequest): Promise<{ jobId: string }>;
  cancelConversion(jobId: string): Promise<void>;
  onJobUpdate(callback: (event: JobUpdateEvent) => void): () => void;
  revealInFolder(path: string): Promise<void>;
  getAppInfo(): Promise<AppInfo>;
}
```

上面是接口草案，不要求逐字实现。每个 API 应有明确输入输出类型；事件监听方法必须返回取消订阅函数，React 组件卸载时要取消订阅。

**不要**暴露 `runCommand(command: string)`、任意 `exec`、整个 `fs` 模块或完整 `ipcRenderer`。每项 API 都只允许执行本项目确实需要的操作。Electron 官方安全指南要求限制渲染进程能力、开启上下文隔离与沙箱，并校验 IPC 的调用来源与参数：https://www.electronjs.org/docs/latest/tutorial/security/

### 安全默认配置

- `nodeIntegration: false`
- `contextIsolation: true`
- `sandbox: true`（按选择的 preload 打包方式确认兼容性）
- React renderer 不直接导入 `node:fs`、`node:child_process` 等 Node 模块。
- 所有 FFmpeg 调用使用 `spawn(executable, args, { shell: false })`；严禁将用户文件路径拼入 shell 命令字符串。
- IPC 参数需验证，文件选择优先使用系统对话框；拒绝不存在的路径、目录冒充视频文件等异常输入。
- 禁止把远程不可信页面作为带 Node 能力的主窗口内容加载。

## 6. 关键数据结构草案

```ts
export interface VideoItem {
  id: string;
  path: string;
  name: string;
  thumbnailDataUrl?: string;
  metadata?: VideoMetadata;
  inspectStatus: 'pending' | 'ready' | 'failed';
  inspectError?: string;
}

export interface ConversionSettings {
  format: 'mp4' | 'mkv';
  videoCodec: 'h264' | 'h265';
  quality: number; // CRF，例如 20–28；UI 要给出简单说明
  outputDirectory: string;
}

export interface ConversionJob {
  id: string;
  sourcePath: string;
  outputPath: string;
  status: JobStatus;
  progress: number; // 0–100
  errorMessage?: string;
  logExcerpt?: string;
  startedAt?: number;
  finishedAt?: number;
}
```

注意：这份结构是接口设计起点，不要直接复制后假设所有字段都已被使用。应根据实际 UI 和主进程行为删减或补齐，并维护一份可信的类型定义。

## 7. 三天实施排期

### Day 1：客户端骨架、FFmpeg 环境、媒体导入

**目标：** 当天结束时，应用能启动，并且能把真实视频导入 UI、读到媒体信息、显示缩略图。

| 时间块 | 任务 | 可验证产出 |
|---|---|---|
| 上午 | 创建 Electron + Vite + React + TS 项目；设置主进程、preload、renderer；确认 `npm run dev` 可打开桌面窗口 | 桌面窗口能启动；网页浏览器单独打开不是验收结果 |
| 上午后段 | 设置严格 IPC API、类型共享与基本安全配置 | renderer 不直接调用 Node 文件系统或 child_process |
| 下午前段 | 配置 FFmpeg/FFprobe 定位、版本检查与友好错误 | 无 FFmpeg 时能告诉用户怎么修复；有 FFmpeg 时显示版本 |
| 下午后段 | 实现文件选择与 ffprobe metadata parsing | 导入文件后显示名字、时长、分辨率、编码和文件大小 |
| 晚上 | 生成缩略图；完善空状态、加载态、失败态；当天进行一次最小 Windows 打包验证 | 真实文件显示缩略图；失败文件不会崩溃；打包链路提前暴露问题 |

**Day 1 结束门槛：** 如果一个本地 MP4 文件不能稳定导入、探测和显示缩略图，不得开始做动画、复杂主题或额外页面。

### Day 2：真正的转码、队列、进度、错误处理

**目标：** 主功能链路跑通，不再是纯 UI 原型。

| 时间块 | 任务 | 可验证产出 |
|---|---|---|
| 上午 | 实现按格式构造 FFmpeg 参数；支持 MP4/MKV；默认兼容预设 | 输出视频可由系统播放器打开；容器与参数匹配 |
| 上午后段 | 实现单任务串行队列和明确状态机 | 多个任务按顺序工作；状态转换可追踪 |
| 下午前段 | 实现 `-progress pipe:1` 进度解析、进度事件与取消 | 进度合理；点击取消能实际终止任务 |
| 下午后段 | 加入唯一文件名、临时输出文件、失败清理和可读错误提示 | 不误覆盖源文件；失败不会留下伪装成完成的视频 |
| 晚上 | 手工测：中文路径、带空格路径、无音轨视频、损坏视频、目标目录不可写、取消任务 | 关键异常可重现、可解释、可恢复 |

**Day 2 结束门槛：** 真实转换至少成功一次，取消至少成功一次，失败至少能被 UI 正确显示一次。

### Day 3：界面打磨、回归、打包与 GitHub 交付

**目标：** 让一个陌生用户能第一次运行、理解和使用项目，并能检查其开发过程。

| 时间块 | 任务 | 可验证产出 |
|---|---|---|
| 上午 | 打磨布局、空状态、缩略图比例、按钮禁用规则、状态颜色、错误详情 | 没有明显假按钮；窗口调整时布局正常 |
| 上午后段 | 自动化测试关键纯函数：分辨率/帧率解析、时长、文件大小、进度解析、命名冲突 | `npm test` 有真实执行结果 |
| 下午前段 | 产出 Windows 安装包或便携版，并在干净启动场景测试 | 不是只在开发模式能运行；FFmpeg 路径在打包后正常 |
| 下午后段 | 补 README、截图、使用步骤、架构图、已知限制、FFmpeg 致谢/许可说明 | 陌生人能按说明启动项目 |
| 晚上 | 清理代码、检查 Git diff、确认文档日志、推送 GitHub、打最终 tag（可选） | 仓库干净；记录只写实际验证过的结果 |

### 三天的时间分配原则

- 不要让编码模型持续“重构整个项目”。一次只允许它处理一个阶段，完成后先跑命令、查看 diff，再进入下一阶段。

- 到第三天如果时间不足，优先保证稳定的 MP4/MKV 转换与交付文档，不要为了支持更多格式牺牲主链路。

### 手工测试必测项

| 编号 | 场景 | 预期结果 |
|---|---|---|
| M01 | 导入单个正常 MP4 | 有缩略图与媒体信息 |

| M07 | 选择 MKV 输出 | 生成有效 MKV；参数中没有误用仅适用于 MP4 的选项 |
| M08 | 两个以上任务排队 | 串行完成；失败的一个不影响后续任务 |
| M09 | 转换中点击取消 | 子进程终止，状态为 canceled，临时文件尽量清理 |
| M10 | 输出文件名冲突 | 自动生成不冲突名称或按明确的用户选择处理 |
| M11 | FFmpeg 不存在/路径失效 | 环境状态可见，错误可读且有修复方向 |
| M12 | 输出目录无写权限 | 显示输出失败，不标为完成 |
| M13 | 缩略图失败但媒体探测成功 | 显示占位图，仍允许转换 |
| M14 | 打包版首次启动 | 不依赖开发目录中的临时文件或开发服务器 |

### 自动化测试优先级

1. `parseRationalFrameRate('30000/1001')`、`parseRationalFrameRate('0/0')`。
2. 格式化秒数、文件大小；未知值不显示 `NaN` 或错误单位。
3. FFmpeg 进度解析与 0–99% 限制。
4. 输出文件命名冲突的唯一命名策略。
5. `ConversionSettings` 到参数数组的映射；确认容器相关参数只在兼容的格式上出现。
6. 状态机：queued → running → completed/failed/canceled，不出现 impossible transition。

### 可选测试素材生成

在已安装 FFmpeg 的测试机器上，可用短视频生成最小测试素材，不必把私人视频提交仓库：

```bash
ffmpeg -f lavfi -i testsrc2=size=640x360:rate=24 -f lavfi -i sine=frequency=1000:sample_rate=44100 -t 8 -c:v libx264 -pix_fmt yuv420p -c:a aac sample-with-audio.mp4
```

再生成一个无音轨样本：

```bash
ffmpeg -f lavfi -i testsrc2=size=640x360:rate=24 -t 5 -c:v libx264 -pix_fmt yuv420p sample-no-audio.mp4
```

如果本机 FFmpeg 构建不包含 `lavfi` 或指定编码器，记录实际错误并改用真实的小型样本，不要声称测试已通过。

## 13. 给开发者的 AI 工程工作流建议

### 不要让弱模型一口气写完整个项目

推荐循环：

1. **你定义当前目标**：例如“阶段 2 只实现文件导入和 metadata”。
2. **模型先读代码并给出小计划**：确认它知道当前目录、已有实现和接口。
3. **模型只做这一阶段**：限制改动范围，避免跨层随意重构。
4. **你运行命令并实际测试**：把报错、行为和截图反馈给模型，而不是只接受它的“已完成”。
5. **模型修复并记录**：提交可读 diff，更新开发日志。
6. **阶段通过后再提交 Git commit**：这样出问题能回滚，也能看出功能是怎样逐步实现的。

### 每阶段代码审查重点

- 是否把 `child_process` 放到了 renderer？
- 是否用 `exec('ffmpeg ...')` 拼接带有用户路径的命令？
- UI 是否用定时器假造进度？
- FFmpeg 非零退出时是否错误显示成功？
- 点击取消是否真正停止进程？
- 是否可能覆盖源文件或已有文件？
- 是否把异常吞掉，只在控制台输出？
- 是否生成没有作用的按钮、设置或导航？
- 是否将没有执行的测试写成通过？
- 是否每次为了加一个功能就重写主架构？

### 最终再让强模型做一次审查

把仓库关键文件、测试结果、`git diff`、开发日志交给强模型，让它重点审查：

- 架构和进程边界是否正确；
- FFmpeg 参数和进度解析有没有明显错误；
- 取消、失败与临时文件清理是否完整；
- 打包后的 FFmpeg 路径是否可靠；
- UI 是否自洽且没有假功能；
- README、测试结果和开发日志是否能被证据支撑。

不要让审查模型在最后阶段不加区分地重写整个项目。要求它先列出 P0/P1 问题，再逐条修复并测试。

## 14. 现成项目与参考建议

参考成熟项目时，**重点研究用户流程、任务状态、错误反馈、项目结构和打包方式，不要直接复制整个应用**。本项目时间只有三天，复杂工具有大量超出本题需要的功能。

### 1. HandBrake：预设和转换队列

- 项目主页：https://handbrake.fr/
- 官方预设说明：https://handbrake.fr/docs/en/latest/technical/official-presets.html
- 官方队列文档：https://github.com/HandBrake/HandBrake-docs/blob/master/source/docs/en/latest/advanced/queue.markdown

借鉴点：把复杂编码选项包装成可理解的预设；转换任务进入队列；明确来源、输出路径和正在处理的工作。不要在三天内照搬它的大量编码细节。

### 2. Shutter Encoder：FFmpeg 工作流与批处理

- 官方文档：https://www.shutterencoder.com/documentation/

借鉴点：支持多文件、输出状态、预设和队列；主工作流围绕“输入文件—选择处理方式—输出位置—开始任务”展开。不要把它庞大的专业选项都塞进 MVP。

### 3. LosslessCut：桌面媒体工具的视觉和交互

- GitHub：https://github.com/mifi/lossless-cut

借鉴点：它是成熟的跨平台 FFmpeg GUI 项目，可研究其桌面体验、键盘交互、媒体文件处理与工程组织。它的主功能是快速无损剪切等，不是本题的逐项实现参考；只借鉴与 FrameForge 相关的模式。

### 4. FFmpeg Studio：技术栈相近的小型参考仓库

- GitHub：https://github.com/igo9go/ffmpeg-studio

仓库说明采用 Electron、React、TypeScript、Tailwind 与 ffmpeg-static，适合快速对照 `electron/`、`src/`、`preload` 和媒体处理模块的分工。但公开说明显示它的提交历史很少，因此应把它视为结构参考，而不是成熟度或稳定性的背书。不要直接复制它的所有功能。

### 5. Electron 官方安全文档

- https://www.electronjs.org/docs/latest/tutorial/security/

必须理解最小暴露 API、上下文隔离、渲染进程沙箱、IPC 校验和不可信内容的风险。把“安全地调用本机子进程”做对，比添加更多 UI 功能更有工程价值。

评审者可能很快判断这个项目是不是“AI 生成的一个界面”。要用可检查的证据展示不同：

| 评审维度 | 该如何体现 |
|---|---|
| 客户端关联度 | Windows 桌面窗口、原生文件选择、本地文件处理、FFmpeg 子进程 |
| 核心功能 | 真实 metadata、真实缩略图、真实编码输出，不用 mock 冒充 |
| 产品可用性 | 空状态、加载态、失败态、进度、取消、输出路径、冲突处理 |
| 工程架构 | 主进程/预加载/渲染进程边界，typed IPC，独立服务层，任务状态机 |
| AI 工程能力 | 任务拆分、分阶段验收、Diff 审核、真实测试、日志记录、范围控制 |
| 交付完整度 | Windows 包、README、截图、测试计划、会话总结、清晰 Git 历史 |

面试或项目介绍时，可重点讲：

> 我没有让 AI 一次性生成整个项目，而是把它拆成桌面骨架、媒体探测、真实转码、队列和交付五个阶段。每一阶段都有明确验收条件，我亲自运行命令与测试，再根据真实错误反馈给模型修复。技术上将 UI 与本地媒体处理分离，使用受控 IPC 管理 FFmpeg 子进程，并针对取消、目标文件冲突、错误清理和打包环境做了专门处理。开发者决策、AI 建议取舍与验证结果都保留在开发日志中。

这段陈述只能在你确实完成对应工作后使用；项目介绍不能替代真实证据。

## 16. 最终交付验收单

- [ ] 项目能在目标 Windows 机器启动。
- [ ] UI 是真正的桌面客户端，不是只有浏览器页面。
- [ ] 支持多视频导入。
- [ ] 每条视频能展示真实元数据。
- [ ] 每条视频能生成或明确展示缩略图生成失败状态。
- [ ] MP4/MKV 转换使用实际 FFmpeg 进程。
- [ ] 任务进度来自 FFmpeg 输出，而不是定时器假进度。
- [ ] 转换完成有有效输出文件；失败与取消有正确状态。
- [ ] 取消进程有效；临时输出可清理。
- [ ] 目标文件名冲突不会静默覆盖。
- [ ] 中文路径、空格路径、无音轨、损坏视频等关键场景已经测试。
- [ ] Windows 打包产物真实运行测试通过。
- [ ] README 的所有命令和使用步骤已经核实。
- [ ] `docs/AI_DEVELOPMENT_LOG.md` 记录了每阶段的真实决策、开发者反馈和测试。
- [ ] `docs/SESSION_SUMMARY.md` 区分已实现、已测试与未验证的内容。
- [ ] GitHub 仓库无私人视频、敏感信息和不该提交的大型文件。
- [ ] FFmpeg 二进制再分发与第三方许可证事项已核对。

**最终原则：一个功能真实、可启动、可测试、可解释的视频转换客户端，胜过十个没有打通的“高级功能”。**
