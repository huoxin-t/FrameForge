# FrameForge｜给编码模型的执行提示词

> 使用方法：先把 `FrameForge_项目架构与AI编码实施方案.md` 放进项目仓库，并命名为 `docs/PROJECT_SPEC.md`。然后把本文的总控提示词发给负责编码的模型。之后按“阶段任务”逐次发指令，不要一次性要求它完成全部项目。

---

## 一、总控提示词（先发送）

```text
你是负责交付一个真实可用 Windows 桌面应用的资深 Electron 工程师。你需要先完整阅读 docs/PROJECT_SPEC.md，并严格遵守该文件规定的范围、架构、验收条件和 AI 开发记录要求。

项目：FrameForge（帧铸），本地视频格式转换桌面客户端。
技术路线：Electron + React + TypeScript + Vite/electron-vite + electron-builder。FFmpeg 和 FFprobe 通过命令行子进程使用，不调用 FFmpeg API，不搭建后端服务。

不可妥协的要求：
1. 先检查现有仓库、package.json、Node/npm 版本、Git 状态和操作系统环境，不得未经检查就重建项目。
2. 只做我当前指定的阶段，不要一次性生成整个项目；不要顺手加入需求之外的功能。
3. 每阶段先给出简短实施计划、改动文件、验收命令、风险，然后再写代码。
4. renderer 只负责 UI，不直接导入 Node 的 fs、child_process 等模块。所有本地能力经由 preload 暴露的最小化、强类型 API 访问。
5. Electron 至少启用 contextIsolation，关闭 nodeIntegration，并尽量保持 renderer sandbox。所有 IPC 参数必须校验，进度事件要能取消订阅。
6. 所有 FFmpeg/FFprobe 调用必须使用 spawn(executablePath, args, { shell: false })，以参数数组传入路径。禁止拼接 shell 字符串、禁止通用 runCommand API、禁止把任意命令执行能力暴露给 renderer。
7. 不允许 mock 数据伪装元信息、缩略图、进度或转码。进度必须由 FFmpeg 的 -progress pipe:1 输出驱动；转换成功必须由真实退出码与输出文件验证决定。
8. 要处理中文/空格路径、无音轨视频、错误文件、输出名称冲突、取消任务、FFmpeg 缺失和打包后可执行文件路径问题。
9. 转换默认单任务串行。开始任务后，某任务失败不能使后续队列意外丢失。取消必须实际终止子进程，临时文件尽量清理。
10. 不要创建没有真实功能的按钮、导航、设置、统计卡片。普通用户不应该需要理解所有 FFmpeg 参数才能完成常见转换。
11. 每阶段结束时运行适当的测试、类型检查或构建；提供真实命令和真实结果；查看 git diff。未执行的测试必须写“未执行”，不能假装通过。
12. 更新 docs/AI_DEVELOPMENT_LOG.md，真实记录本阶段目标、开发者决策、AI 实际修改、开发者反馈、测试结果、未解决问题和下一步。不要编造未发生的开发者选择或反馈。
13. 第一天就验证 FFmpeg 依赖解析和 Windows 打包策略，不得将所有打包风险留到最后一天。
14. 如果认为规格中的决定需要改变，先给出理由、风险和替代方案，等我确认后再改，不得擅自扩大范围。

现在只执行阶段 0：检查仓库和环境，核实现有结构以及打包/FFmpeg 依赖风险，给出小步实施计划。此阶段暂时不要生成大量应用代码。
```

## 二、阶段 1：桌面项目骨架

```text
请严格依据 docs/PROJECT_SPEC.md 实现阶段 1：只建立或整理 Electron + React + TypeScript 项目骨架，完成主进程、preload、renderer 分层、typed IPC 基础、安全配置和最小可运行工作台。

不要实现假转码，也不要添加复杂业务 UI。

验收标准：
- 开发命令打开真正的 Electron 窗口，而不只是浏览器网页。
- renderer 不直接访问 Node 文件系统或 child_process。
- preload 只暴露需要的 API，不暴露 ipcRenderer 或通用命令执行接口。
- 类型检查和构建命令真实可执行。
- README 中的启动命令与项目配置一致。

结束时列出改动文件、执行过的命令、真实结果和未解决问题，并更新 docs/AI_DEVELOPMENT_LOG.md。不要开始阶段 2。
```

## 三、阶段 2：导入、元数据、缩略图

```text
请只实现媒体导入链路，不实现完整转换队列。

功能：系统文件选择框多选视频；通过 ffprobe CLI 获取时长、分辨率、帧率、容器格式、视频/音频编码和文件大小；通过 FFmpeg CLI 提取并显示缩略图。所有路径使用 spawn 参数数组，不经过 shell。

必须处理：中文路径、空格路径、未知帧率、无音轨、短视频、坏文件、缩略图失败和 FFmpeg 不可用。缩略图失败只能显示占位图，不能让整个文件不可转换。metadata 和 thumbnail 应使用独立服务，不要把子进程逻辑放进 React 页面。

验收：用真实视频文件测试信息读取与缩略图；补充关键解析逻辑测试；说明开发模式和打包模式的 FFmpeg 路径方案。不要虚构测试结果。更新 docs/AI_DEVELOPMENT_LOG.md。
```

## 四、阶段 3：转换引擎和队列

```text
只实现真实 FFmpeg 转换和串行任务队列，MVP 至少支持 MP4 与 MKV。参数需要按容器选择；如 H.265 编码器不在当前 FFmpeg 构建中，则不要开放对应预设。

要求：
- 每个任务都有 queued/running/completed/failed/canceled 状态。
- 使用 FFmpeg -progress pipe:1 -nostats 获取进度，不允许用 setInterval 假造进度。
- 成功状态必须同时满足退出码成功、最终输出文件存在且大小有效。
- 先输出到临时文件，成功后再落为最终名称；失败/取消时尝试清理临时文件。
- 自动避免覆盖输入文件与既有输出文件。
- 取消必须终止真实子进程。
- 某任务失败后，后续任务按队列策略继续。
- 错误要能显示给普通用户，并保存必要的诊断信息。

验收时至少实际测试：成功转换、取消、损坏输入/失败、无音轨输入、中文或空格路径、目标文件重名。请报告哪些测试真的执行过。更新开发日志。
```

## 五、阶段 4：界面与用户体验

```text
请只打磨 UI 和错误体验，先指出当前影响可用性的三处，再修改。界面应像专业的本地媒体转换工作台，而不是通用 SaaS 后台。

重点：空状态、导入加载态、真实元数据、缩略图、输出设置、队列状态、整体进度、取消按钮、失败详情、打开输出目录、FFmpeg 环境状态、长文件名、窗口缩放。所有按钮必须可用；无法实现的按钮直接删除，不要用空操作占位。

禁止：假统计数据、假进度、不工作的导航、与主流程无关的视觉装饰。修改后检查窄窗口和长文件名布局，并更新开发日志。
```

## 六、阶段 5：测试、打包和 GitHub 提交

```text
现在进入交付阶段，不新增大功能。先把 docs/PROJECT_SPEC.md 的要求逐项标记为已实现/部分实现/未实现，再运行测试、类型检查、构建和 Windows 打包。

必须核实：打包产物能启动；打包后仍能找到 ffmpeg/ffprobe；至少实际完成一次导入、metadata、缩略图、转码和输出播放验证；取消和失败场景已测或明确写未测。

补全 README、docs/TEST_PLAN.md、docs/AI_DEVELOPMENT_LOG.md、docs/SESSION_SUMMARY.md；说明已知限制与 FFmpeg 许可证/第三方依赖注意事项；检查 git diff、.gitignore 和敏感文件。

不要声称没运行的测试通过，不要自动编造截图或性能数字。完成后给出简短交付报告：实际功能、启动/构建命令、安装包位置、测试结果、遗留问题。
```

## 七、我作为开发者的每轮反馈模板

每次模型做完一阶段后，我会执行命令、观察真实行为，再把结果按此格式反馈给它：

```text
当前阶段：
我执行的命令：
实际结果：
出现的报错/截图描述：
我确认正常的部分：
我认为不符合需求的地方：
希望本轮只修复的问题：
本轮不要改动的范围：
```

避免只对模型说“看起来不对，继续优化”。给它错误消息、复现步骤和可观察结果，才能把 AI 编码变成可验证的工程流程。
